From 0 to 1: how Kiro Lab grew

2026-05 → 2026-11: a test engineer gradually handing the daily, repetitive cognitive work (reading regression results, root-causing, writing issue reports, comparing versions) to an agent.

⓪

Phase 0 · Start: write down how you work

Pain: every conversation re-explained preferences and process.

Built: one agent + workflow.md (process and red lines) + preferences.md (personal preferences), auto-loaded as resources every session; everything in git.

Replicate: git from day one; make deletions a red line (explicit confirmation, scoped paths).

2026-05 · Week 1
①

Phase 1 · Daily use: triggers + daily flow

Pain: the fixed morning routine (check results, handle to-dos, write the daily report) had to be dictated every time.

Built: trigger words routed to rules/*.md; daily flow, daily report, pending queue (cron writes to pending/); HTML report templates + index page; decision log. Lab side: scope result check and upgrade break dashboard used every day; analysis grew into L1/L2/L3 via manual root-causing → error patterns → semantic TR matching (2753 TRs).

Replicate: start with the one or two features you truly use every day; let the rest grow around them.

2026-06 – 07
②

Phase 2 · Memory and methodology

Pain: history kept growing and became unfindable; the same mistakes recurred.

Built: session history archived daily, Memory Dream every 7 days (Orient → Gather → Consolidate → Prune); workflow-patterns promoted to discipline when mature; self-checks via kiro-doctor / validate-kiro / kiro-audit; reviewer sub-agent + review-artifact.py (script measures, agent judges), with a push gate too.

Replicate: cap pattern files (lines / entries); when over, merge or promote.

2026-08 – 09
③

Phase 3 · Governance: keep agent actions in check

Pain: more and more write actions (deleting files, push, config changes) guarded only by prompts; sub-agents slow and opaque.

Built: Action gate (10-23) tiered DENY / L3 / L2 / L1 / L0, shadow for about 3 weeks before enforce, L3 approved only in the user's own terminal; run-agent.sh process-boundary calls (10-16) + delegation template; startup check moved into an agentSpawn hook (10-20); kiro-pure split out (10-22 / 10-26) with 76 framework files byte-identical on both sides.

Replicate: kiro-cli lets actions through when a hook crashes (fail-open), so the gate must handle every error path; a bad config must fail to load (fail-closed).

2026-10
④

Phase 4 · Tuning: fewer false positives, harder rules

Pain: gate false positives interrupted normal work; some rules kept being violated despite being written down repeatedly.

Built: variable tracking, read-only command detection, kiro-gate grant batch approval (11-12), plain push to own repos lowered to L2 (11-17), every change replayed against command history; a hanging-search-tool rule violated 6 times → tool removed from the agent's tools; recurring tcsh syntax errors → optional shell_lint in the gate (11-25).

Replicate: once a pattern count passes 2 and keeps rising, stop adding text and find an enforcement point (tool list, hook, config validation).

The recurring loop

Real pain / user correction → logged in workflow-patterns (with count + examples)

→ Recurs: promote to discipline, or turn into a script / template

→ Still violated: enforce in code (config / hook / gate), shadow first, then enforce

→ Decision recorded in decisions/ (alternatives, rationale, review trigger) → evolution log derived from git log by script

Every phase

5 core principles

  1. Need-driven, no upfront architecture.Every mechanism maps to a real pain point; no pain, no feature. Three-layer analysis, memory consolidation and the gate all grew organically.
  2. Only what is written down counts.One user correction → immediately written into a rule file and committed. A verbal 'next time' means nothing was done.
  3. A text rule keeps failing → enforce it in code.If a written rule keeps being broken, self-discipline is not reliable; switch to a hook / config / script check.
  4. Records are generated, not remembered.Evolution logs, indexes and stats are derived by scripts from git log / logs, never hand-written.
  5. Observe before you block.Any enforcement runs in shadow (log-only) first; replay real data to confirm the false-positive rate, then switch to enforce.

Pitfalls (unvarnished)

  • Two rule directories with the same name → the startup check read the wrong one and reported missing files. Clean up old files promptly.
  • Bulk-editing HTML with regex → cross-tag replacement broke 60 a and 17 div closing tags. Edit HTML one spot at a time and validate structure afterwards.
  • A script that does half the flow → it updated the list but never inserted the card; relying on 'I'll remember to do it by hand' failed. Put the whole publish flow in one script.
  • Report numbers written by the model → fabricated stats appeared. Numbers must be computed by scripts, then filled into templates.
  • Pushing back from the shared core → overwrote newer upstream fixes. Fix the direction: change upstream, pull downstream.
  • Hooks fail open by default; tool names vary by client → test the gate against the tool_name actually received, not just the documented name.
