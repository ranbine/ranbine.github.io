Kiro Lab 权限机制：三道关Kiro Lab Permissions: Three Checkpoints

2026-10-23 · bin/action-gate.py · contexts/rules/gate-policy.json

workflow.md 里写的红线只能约束模型「想不想做」；action gate 在执行那一刻用代码检查「能不能做」。这一页讲清楚一次动作如何过关、风险怎么分级、L3 如何审批、规则每周如何演进，以及它做不到什么。 The Red Lines written in workflow.md only constrain what the model intends to do; the action gate enforces them in code at execution time. This page covers how one action passes the gate, how risk is tiered, how L3 approval works, how the rules evolve weekly, and what the gate cannot do.

① 为什么需要代码层的关卡① Why a gate in code

文字规则靠模型自觉，出错时没有任何东西拦住它。gate 挂在 kiro-cli 的 preToolUse hook 上，在工具真正执行前做决定。先在 kiro-cli 2.26 上实测了 hook 的行为：Written rules rely on the model behaving; when it slips, nothing stops it. The gate sits on kiro-cli's preToolUse hook and decides before the tool actually runs. The hook behavior was measured first on kiro-cli 2.26:

实测项Probe结果Result
hook 收到什么Hook input原始 tool_name + tool_inputraw tool_name + tool_input
如何拦截Blockingexit 2 阻止执行，stderr 原样返回给模型exit 2 blocks; stderr goes back to the model
hook 崩溃 / 超时Hook crash / timeoutFAIL-OPEN 工具照常执行the tool still runs
结论：不能依赖 CLI 兜底。gate 脚本自己处理每一条失败路径 —— enforce 模式下任何异常都按拒绝处理（fail-closed）。Takeaway: the CLI is no safety net. The gate script handles every failure path itself — in enforce mode any internal error is treated as a block (fail-closed).

⑤ L3 审批⑤ L3 approval

L3 · gate_id
  1. 拦截消息告诉模型：停下来，向用户请求批准。The block message tells the model to stop and ask the user.
  2. 用户在自己的终端里运行 kiro-gate approve <gate_id>。The user runs kiro-gate approve <gate_id> in their own terminal.
  3. 在 kiro-cli 下（存在 KIRO_* 环境变量或 kiro-cli 祖先进程）或没有 tty 时，approve 直接拒绝。approve refuses under kiro-cli (KIRO_* env or a kiro-cli ancestor process) and without a tty.
  4. 用户必须把 gate_id 再手动输入一遍。The user must type the gate_id back.
  5. 批准 = sha256(tool, 去掉 __tool_use_purpose 的参数, cwd)，一次性，10 分钟有效；改动一个字符 → 需要新的批准。Approval = sha256(tool, args without __tool_use_purpose, cwd), one-shot, 10 min; change one character → new approval.

⑦ 每周审计⑦ Weekly audit

思路和 Memory Dream 相同：原始记录 → 定期整合 → 人来决定。但它是单独的一步，因为：它改变的是权限边界；它是双向的；它的信号是结构化的。Same idea as Memory Dream — raw records → periodic consolidation → human decides — but a separate step, because it changes permission boundaries, it is two-way, and its signal is structured.

方向Direction触发条件Trigger提案Proposal
放宽relax某个 L2 key 在 ≥2 个 session 中被放行 ≥5 次an L2 key allowed ≥5 times in ≥2 sessions提议 L1，且仅限自己目录propose L1, limited to own dirs
收紧tighten有风险的 L2 模式，如 curl POST / ssh / killrisky L2 patterns like curl POST / ssh / kill提议 L3propose L3
apply 只会新增规则。分级顺序是 DENY > L3 > L0 > L1，所以新增的 L1 永远不能压过已有的 L3；L3 从不被降级。职责分离：脚本提案，reviewer 评判，只有用户能 apply。apply only adds rules. Since classification order is DENY > L3 > L0 > L1, an added L1 can never lower an L3; L3 is never downgraded. Separation: the script proposes, the reviewer judges, only the user applies.

⑩ 局限（坦白说）⑩ Limits (honestly)

  • 防失误的护栏，不是沙箱。同一用户身份下刻意混淆，可以绕过字符串规则。A guard-rail against mistakes, not a sandbox. Deliberate same-user obfuscation can get around string rules.
  • L2 还没有实时审查。为 L2 引入 gate agent 是之后的选项。L2 is not reviewed in real time yet. A gate agent for L2 is a later option.
  • 目前是 shadow 模式。看过 kiro-gate stats 后再切 enforce。Currently shadow. Enforce after reviewing kiro-gate stats.
